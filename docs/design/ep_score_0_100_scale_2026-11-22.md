# EP score on a 0-100 scale — design (2026-11-22)

Operator ask, 2026-11-22: *"I want to revisit the scoring scale so numbers 0-100 vs random scale now."*

Status: DESIGN ONLY. Nothing here is built, committed or deployed. The mapping, the bar's number and the history handling are his decisions (section 8).

## Summary for the operator

- **Recommended: drop the "+15" and keep the rest: scores run 0 to 97.5 and the alert bar reads 50 instead of 65.**
- **What alerts and what trades does not change:** the bar moves through the same formula as the score, checked on every reachable score (section 3).
- **No ties at the top:** best score is 81 in a normal market and 97.5 in Bull; a hard cap at 100 would show seven different Bull score levels as the same "100".
- **Old stored scores stay as written, with a scale tag;** readers convert (a score stored since 08-22 is simply 15 lower on the new scale).
- **critic: one gap in the proof — the score number is fed as text to the theme-grouping model, whose output reaches the grading judge, which sets the alert tier.** The fix keeps that model's input number on the old scale, so its input does not change (section 9, C1).
- **Action: seven calls for you in section 8** (mapping, bar shown as 50, Bull display, revert side, history, one label fix, timing); build and deploy wait on them.

A fifth variant, divide by 78 so the Bull top is exactly 100: bar lands on 51.3, not a whole number, multiplier not binary-exact. Rejected for the same two reasons as A.

**Recommendation: D.** One-line reason: it is the only mapping that gives a whole-number bar, keeps the exact rounding proof, loses no ranking information, and leaves every additive sort key in the same order.

Three honest costs of D:
- **Headroom is 2.5 points.** The Bull top is 97.5. One new +5 rubric component would push it to 103.75. Handled by a CI guard that fails the build (section 3.3), not by a cap; the 100 cap was removed on 2026-05-09 (#42) because it tied three names at 100.
- **The number 50 already has a meaning.** It was the legacy MODERATE cutline, and the old "ep >= 50" theme rule. After the change 50 = the alert bar. Section 5 lists each place the old 50 appears.
- **The top is 81, not 100, outside Bull.** If "100 = perfect" matters more than "bar = 50", that is mapping A or the divide-by-78 variant, with their costs.

Worked examples under D (old shown -> new shown): bar 65 -> 50; conviction-floor game-changer 90 -> 75 (Bull 105 -> 90); best normal-market score 96.2 -> 81.2; best Bull score 112.5 -> 97.5; a zero 15 -> 0.

## 3. Proof that alerts, tiers and entries do not change

### 3.1 The argument (same as #533, 2026-08-22)

1. **One decision point.** The only live comparison of score to bar is `ep_detector.py` L6260 (skip if score < bar) and L6274 (HIGH if score >= bar). Everything downstream keys on the stored tier, not the number.
   - critic: **TRUE for code comparisons, FALSE for model inputs.** The holistic judge is load-bearing (`ep_grade_judge.py` L8-13: its tier overwrites `score_tier`; it can set 'none'). Its prompt does not print `ep_score` (checked: only the payload dict, L305), but it does receive `active_narratives`, and those are produced by the Lane-2 grouping model, whose prompt prints `ep {ep_score}` for every stock (`theme_engine.py` L767 v2, L970 v1). The code calls Lane-2 "GRADE-AFFECTING ... can change grades and therefore trades" (`db.py` L6392-6395). A monotone transform says nothing about what a language model does when the number it reads changes. See section 9, C1.
2. **Same function on both sides.** The score and the bar both go through `apply_output_scale`. New bar = T(40) = 50. A strictly increasing function preserves `score >= bar`.
3. **The transform stays the last step.** It sits after the conviction floor (a raw value, applied before the multiplier) and after the regime multiplier. Neither moves. The floor stays raw 60.
4. **Rounding cannot flip the boundary.** The input is already rounded to 1 decimal. 39.9 -> 49.875 -> 49.9 (below 50). 40.0 -> exactly 50.0. 1.25 is 5/4, exact in binary.
   - critic: the DECISION holds (re-checked: 0 flips on n=1,301, new == old - 15 at every point, 0 display collisions on the 69 reachable values). The TEXT does not: a reachable Bull score, raw 33 x 1.2 = 39.6, shows as 49.5, and every renderer formats with `:.0f`, which rounds 49.5 to "50". So the skip reason reads **"score 50 < bar 50"** (`ep_detector.py` L6263), and the near-miss block lists "score 50" under a "35-50" label (`briefing.py` L521). Today the same row prints "64 < bar 65" (64.5 rounds half-to-even to 64), so this is a new contradiction. Fix: format sub-bar scores to 1 decimal (or round down) in the skip reason and the near-miss line; add 39.6 to test 3.
5. **Checked numerically for this design:** on the 0.1-step grid (n=1,301): 0 boundary flips, strictly increasing everywhere, and new = old - 15 at every point. On the reachable scores (n=69): 0 mismatches.
6. **The revert side is not touched.** `SCORE_WEIGHTS_LEGACY["output_scale"]` stays None.

### 3.2 What the proof does NOT cover

A monotone map protects comparisons of a score to a bar that went through the same map. It does not protect a hard-coded number or a sum of the score with something else. Those are section 5, group 2. With mapping D the additive sums keep their order (a constant shift); with A, B or C they would not.

### 4.3 H2 in detail

- **New column** `ep_score_scale SMALLINT` on the tables that carry a bare score with no stamp: `mi_ep_alerts`, `mi_live_trades`, `mi_paper_trades`, `mi_lowcap_paper_lane_alerts`, `mi_live_fill_counterfactuals`, `mi_catalyst_tier_shadow`, `mi_ep_slot_rank_shadow`, `mi_theme_axis_shadow`, `mi_delayed_entry_watch`, `mi_delayed_entry_trigger`, `mi_cap_plus_one_shadow` and the missed-outcomes tables. Tables that already carry a stamp (`mi_ep_scan_log.ep_bar` + `score_side`, `mi_ep_score_shadow.sep_bar`) need no column: bar 50 is a new, unambiguous value there. `mi_ep_theme_belonging_shadow` gets the column (see 4.1).
- **No column default.** Every writer stamps explicitly from one constant, `CURRENT_SCALE_VERSION`. NULL means "not stamped: resolve by date", never "current".
- **Back-fill of the tag (not the score):** 1 before 2026-08-22, 2 from 08-22 to the switch, with 08-22's own rows and any switch-OFF days set from the scan log (`score_side`, `ep_bar`) joined on ticker and date.
- **One helper** in `ep_rubric.py`: `score_on_current_scale(score, scale_version) -> (value, converted_ok)`. Version 3: unchanged. Version 2: minus 15. Version 1b: x 1.25. Version 1: returned as-is with `converted_ok=False`; renders say "old scale".
- **The old scale stays as a named constant** (`OUTPUT_SCALE_V2 = {mult 1.25, offset 15}`, bar 65) so `/why`, `_lattice_prevented_alerts` and `scripts/ep_replay.py` can rebuild version-2 rows. `rule_eras.py` gets a third dated switch.
  - critic: **not in either existing table.** `ADMISSION_SWITCHES` would relabel every fill from the switch as a new admission era with an identical filter set. The module warns against exactly this (`rule_eras.py` L285-292, "splitting the #482/#593/#617 admission_era segmentation for nothing"). `EXIT_SWITCHES` would put "rules changed" into the weekly review's era sentence (#662) and split the exit era counts. Use a separate `SCORE_SCALE_SWITCHES` that only score readers use.
- **Preconditions (three $0 queries, none run yet; run before the build is called done):**
  1. Was the separation switch ever OFF since 08-22, and what does 08-22 itself hold? `SELECT scan_date, score_side, ep_bar, count(*) FROM mi_ep_scan_log WHERE scan_date >= '2026-08-22' GROUP BY 1,2,3 ORDER BY 1`. Any `legacy` rows, or bar-40 rows, mean those rows are not version 2 and the tag must carve them out.
  2. What is the largest stored version-2 score? `SELECT max(ep_score) FROM mi_ep_alerts WHERE alert_date >= '2026-08-22'`. Before the 11-22 float change the Bull top was 120 on the old scale, which converts to 105. **So a converted historical score can read above 100.** That is correct history, not a bug; the render should not clamp it.
     - critic: the real ceiling is higher. The Perplexity agreement boost (x1.2) multiplied into the score until it was retired on 2026-08-27 (`ep_detector.py` L5168-5181), so for 08-22 to 08-27 the top multiplier was 1.2 x 1.2 = 1.44: raw 70 x 1.44 = 100.8 internal = **141 old, 126 new**. `ep_score_math._mult_label` already names "older agreement boosts". The helper and `/why` must accept multipliers other than 1.0 and 1.2 on those rows.
  3. Does every stored alert sit at or above its bar (needed for the theme rule in section 5)? `SELECT min(ep_score) FROM mi_ep_alerts WHERE alert_date >= '2026-08-22'`; expected 65 or higher.
