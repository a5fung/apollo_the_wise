## A. Decisions (each with the reason)

**D1 — One batched multi-symbol bars call per tick, full day-so-far, no in-memory bar cache.**
- `alpaca-py 0.43.2`: `StockBarsRequest(symbol_or_symbols: list[str])` is comma-joined into `symbols=`; `StockHistoricalDataClient._get_marketdata` pages at **10,000 bars per HTTP request across all symbols** and follows `next_page_token`. So requests/tick = ceil(N × bars-so-far / 10,000), not N.
- Request budget (computed): 350 names → 1 request at 09:35, 3 at 10:35, 7 at 12:35, **14 at 15:55**, **~2,800/day** (today: 350/min, ~133,000/day). 184 names → peak 8/min, ~1,560/day. Both sit under the 200/min data-API floor (the free tier) with room; the Algo Trader Plus tier (10,000/min) is irrelevant.
- Chunking: symbols-per-request = `min(BARS_CHUNK_MAX=200, 10_000 // (last_completed + 1))` so each request is one page (URL ≤ ~1.3 KB); the SDK's own pagination stays as the safety net if a chunk spills. One chunk failing loses one chunk's names for one minute, never the tick.
- Full-day refetch, not incremental: a late/revised minute bar under an incremental fetch would under-count cumulative volume and flip F1; full refetch keeps the module's "nothing from memory" rule (docstring lines 37-43). Incremental is the named fallback only if the Saturday probe (D8) exceeds budget.
- Not a stream: `bar_stream.py` lives 09:30-09:35 for a handful of ORB names; an all-day 350-name subscription is new stateful code for no measured need.
- Per-tick wall time at 350 names (estimate — latency is an assumption the fake-client test cannot measure; D8 measures it): 09:35 ~1 s; 15:55 ≤ 14 sequential requests × ~0.3-0.5 s ≈ 5-7 s + `bars_by_minute`/`evaluate` over ~135k bar dicts ≈ 0.5 s + ≤ 5 per-name broker calls for names with rows + ≤ 5 funnel submits (~1-2 s each). Worst case ≈ 15-20 s against the job's budget: `second=10, max_instances=1, coalesce=True, misfire_grace_time=30` (scheduler.py:7918-7925) — a tick over ~45 s skips the next minute, never overlaps.
- The fill-check's own fetch (`_check_stop_at_fill_once` line 1183, ≤ 5 filled rows) is left per-name.

**D2 — Slots: a per-tick pre-count with the funnel's own SQL; eligible names in `list_rank` order; the overflow is HELD, not skipped.**
- Fact: `bv1_get_list` returns `ORDER BY list_rank` (db.py:19995-20002), so within one tick the loop already submits in score order. What makes today "first-to-break" is the funnel: a `block:max_positions` goes through `_skip(...)` → `_insert_skipped_trade` → a `status='skipped'` row (entry_pipeline ~line 870-900; live_tracker:2336) which the next tick reads as `row_skipped` (entry line 1368-1370) — **terminal for the day**. With 150-350 names the first tick with 6+ pace-permitted names would kill every name past the 5th for the whole session.
- Stage 2: once per tick, after the switch/strategy checks and after pass 1 (existing rows managed — a pace-lapse cancel this minute frees its slot this minute), read `free = MAX_CONCURRENT_LIVE_POSITIONS − count_open_positions(conn, 'paper')` with `live_tracker.count_open_positions` (the single-SoT count the funnel and `_check_safeguards` share, live_tracker:106-126; counts `filled, order_placed, confirmed` of EVERY paper strategy — the small-cap lane's rows included, per his F2 ruling). Pass 2 walks eligible no-row names (`status == 'ok' and f1_ok`) in `list_rank` order: the first `free` go to the funnel (its advisory-locked recount still rules); the rest are HELD — `_note(today, ticker, "slots_full", ...)`, no funnel call, no row — and retry next tick. `free` decrements on `ACTION_AUTO_ENTERED`.
- A held name that gets a slot later is judged at that moment's price: `width_at_expected_fill` (line 266-283) uses latest × 1.002, so a name that ran away abstains `setup:stop_too_wide`. No new late-entry rule.
- Lane rows (`magna53_smallcap`) count and are never touched; if the lane holds all 5, breakout holds. Filled rows are never displaced under any answer.
- Residual race, stated: the pre-count is advisory; a same-moment lane entry can still produce today's terminal skipped row via the funnel. The lane enters at 09:31, breakout starts 09:35:10 — rare. The funnel is NOT touched Saturday (shared money-path code).
- **Displacement** (cancelling a lower-ranked RESTING unfilled breakout buy to seat a higher-ranked name when `free == 0`) is the strict reading of "highest first, not first-to-break" — and it cancels a trade the current discipline would keep. That is his (Q1 below). Stage 2 ships HOLD-ONLY and PINS it in a test; displacement is a 1-function add (`_outranked_resting(rows_by_rank, eligible_rank, free) -> rows to cancel`, planned cancel with a new `SETUP_BREAKOUT_OUTRANKED = "setup:breakout_outranked"`) if he rules for it.

**D3 — The Telegram list drops its `/bgrade` line only; the command stays.**
- `breakout_v1_list.py:218` is the one line. The command (`agent.py:3474` handler, `channels/telegram.py:1829` CommandHandler + `:1894` BotCommand, the two `preflight_db_updates.py` registrations, `format_ungraded`'s usage line) stays: removing it touches `channels/telegram.py` → orchestrator scope, `deploy.sh both`, the command-parity preflight — for no ruling. **D5 — Audit volume bounded.** `_note` already dedups per (day, ticker, state) (line 361-368): ~1 row per name per state change (≈ 350-700 rows/day at 350 names, first tick writes ~350 sequential inserts ≈ 1 s). Kept as is; a per-tick summary row is a cut-able nicety. Abstain `skipped` rows (`stop_too_wide` etc.) scale the same way (today ~10/day at 27 names → ~100+/day at 350; readers found are counts only: `channels/telegram.py:805`, `system_audit.py`).

**D6 — `evaluate`/`bars_by_minute` untouched.** The batch returns `{ticker: [bars]}` in exactly `get_minute_bars_range`'s dict shape (`t_et, open, high, low, close, volume, vwap`); a symbol absent from Alpaca's answer → `[]` → today's `wait` (`no_minute_bars_yet`), never an abstain; a symbol whose chunk raised → absent from the dict → `wait` + one `breakout_v1_bars_unreadable` audit row per tick naming the chunk.

**D7 — Switch-off path still makes zero bars requests** (verified by reading 11-02, not yet pinned: `test_the_switch_off_places_nothing_and_cancels_a_resting_buy` asserts no funnel call, not zero fetches). Pinned in T9.

No order path. This turns the D1 latency assumption into a number and is stage 2's positive observable while the switch is off.
