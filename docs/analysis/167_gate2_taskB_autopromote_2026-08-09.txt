=== HEADLINE (corrects the task's framing) ===
The auto-promote path from `narrative_cogap` proposals into live `mi_themes` is NOT
dormant or hypothetical — it is ALREADY FIRING IN PRODUCTION TODAY, independent of the
v2 question. `discover_narrative_themes` branches exclusively on the v2 flag
(`if v2: <registry mode> else: <v1, today's-alerts-only mode>`) — v1 and v2 can never
run in the same nightly cycle. Confirmed live: `lane2_grouping_v2` has no row in
`mi_safeguard_state` (fail-closed) -> v1 is what's running now. And v1 already writes
`source='narrative_cogap'` cohorts that clear the >=3-member bar and get auto-promoted:
  2026-07-31: "AI data center infrastructure buildout" {BLZE, FLNC, MPWR} (3 members) ->
              promoted same night (mi_themes: 2026-07-31, Nascent, shadow_promoted).
  2026-08-04: "AI Data Center Infrastructure Buildout" {BTDR, AMRC, BLZE} (3 members) ->
              same pattern, different case in the name.
So flipping v2 does NOT open a new live-mi_themes door. It changes what walks through a
door that is already open and already in use TODAY — from 3-member same-day snapshots
to a 12-member roster carried seven weeks under a stable name. That is the real risk
surface, and it is a shape change, not a go/no-go on auto-promote ever touching mi_themes.

=== What promote_shadow_themes would NAME it + collision check ===
Name is carried unchanged from the shadow proposal: "AI data center infrastructure
buildout" every time (v2's registry reuses the SAME roster name across joins by
design — this is NOT canonicalization at work; _canonicalize_theme_names only renames
when a PRIOR 14-day row has the exact same ticker SET under a different name, and this
cohort's ticker set changes on every join, so that path essentially never fires here).
COLLISION: real, found in live data, but not the cross-lane clobber first suspected.
Both actual same-name promotions found above (7/31, 8/04) are v1 narrative_cogap rows
on DIFFERENT theme_dates — not two sources colliding in one run. Checked whether two
DIFFERENT allowlisted sources (e.g. shadow_v2 + narrative_cogap) could silently
overwrite each other's row same-night: get_shadow_theme_candidates uses
`SELECT DISTINCT ON (name) ... ORDER BY name, run_date DESC` ACROSS ALL allowlisted
sources in ONE query, so within a SINGLE promote_shadow_themes run, two same-named
cohorts from different sources collapse to ONE row (latest run_date wins) before
_upsert_promoted_theme is ever called — a same-run clobber cannot happen this way.
What IS structurally true: _upsert_promoted_theme's ON CONFLICT guard
(`WHERE mi_themes.source='shadow_promoted'`) does not check WHICH upstream source
wrote the prior promoted row, so a LATER separate run proposing the identical name
from a DIFFERENT upstream source could overwrite an earlier promotion's membership on
that (theme_date, name) key. Not observed in the ~30 days of mi_theme_candidates_shadow
/ mi_themes history checked here (the 7/31 and 8/04 collisions are same-source,
different-day). Net: a genuine, already-recurring name-collision risk between v1's own
same-day proposals and what v2's 7-week-carried roster would write under the identical
name — this is what v2 changes, not whether the door exists.

=== Reversibility ===
Confirmed empirically from the live mi_themes history for this exact theme name (only
2 rows exist): 2026-07-31 Nascent/shadow_promoted/{BLZE,FLNC,MPWR}, then 2026-08-03
Retired/live/{} (tombstone, empty tickers). Mechanism: theme_engine.py's nightly
"lost theme" reconciliation (~lines 6456-6522) — any name present in `existing`
(get_active_themes, the 7-day-recency-capped active list) but NOT reproduced in that
night's freshly-computed `all_themes` gets a synthesized Retired row, written as part
of the SAME nightly run that notices the absence. This fired within ~1 trading day of
the promoting lane going quiet (Fri 7/31 -> Mon 8/03, a weekend in between) — faster
than, and independent of, the 7-day `stale_after_days` visibility cap (that cap is a
secondary backstop governing whether a not-yet-tombstoned row still reads as "active"
to readers; it is not the primary retirement trigger observed here). Net: yes,
reversible, and empirically fast — no manual /removetheme needed to clear a one-off
promotion once its own lane stops re-proposing it.
