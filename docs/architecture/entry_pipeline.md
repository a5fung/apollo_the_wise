## Entry Pipeline

- **`broker/entry_pipeline.py::submit_trade_entry`** — single funnel for both MAGNA53 EP and 9M Day 2 entries. Strategy differences (stop source, sizing) inject via `spec_builder` callback. Pipeline owns: dedup → safeguards (cheap early gate) → bar-fetch retry → fade guard → spec build → per-strategy sizing multiplier → **atomic cap-recheck + DB insert (+ auto-enter confirm flip) in one transaction under a per-`account_mode` `pg_advisory_xact_lock` (#461, `_CAP_LOCK_NAMESPACE = 0x434150 "CAP"`; recount via the shared `live_tracker.count_open_positions` — closes the STEP-2→insert TOCTOU race; cap-blocked recheck returns the byte-identical `block:max_positions` / `block:strategy_position_cap` skip + a `cap_recheck_blocked` audit event; no external I/O inside the lock)** → Alpaca submit (post-commit) → audit log → Telegram. **Contract: every terminal failure Telegrams via `humanize()`.**
- `account_mode` resolved at safeguard step from `strategy.phase` via `resolve_account_mode_for_strategy()` and threaded through spec_builder, alpaca client calls, DB inserts, and Telegram surfaces. SpecBuilder type alias takes account_mode as 4th positional arg.
- Bounded action vocabulary: `ACTION_AUTO_ENTERED / PROPOSED / AUTO_ENTER_FAILED / PROPOSAL_SEND_FAILED / SKIPPED / BLOCKED`.
- Bounded skip-reason vocabulary in `broker/skip_reasons.py` — 38 constants across `filter:* / setup:* / block:* / infra:* / window:* / broker:*`. Aggregate via `split_part(skip_reason, ':', 1)`. `broker:*` (#500, 2026-07-23) = the BROKER killed an accepted entry (cancel/reject/expire) — written with a synthesized last-vs-trigger diagnosis by `order_manager.broker_terminal_reason` (WS `_handle_cancel_or_reject` + `check_fills` polling backup), never the pre-#500 bare `"cancelled"`.
- **#490 real-time gap re-check at submission — ⚠ SHIPPED AND `ep_rt_entry_gap_recheck` IS ON (global), flipped 2026-08-02** (built 2026-08-01; this line read "BUILT OFF" for four weeks until `scripts/live_rules.py` was first pointed at `docs/architecture/` on 2026-08-29): stage **4b**, beside the fade guard and before sizing — `check_rt_gap_floor` re-reads `get_latest_trade` and compares against `MIN_GAP_PCT` using `db.get_prev_close` (the detector's own Polygon denominator, so scan and entry cannot disagree). ## Stop-Leg ID Capture

- `alpaca_client.extract_stop_leg_id(order)` is the canonical helper — uses `stop_price` as primary signal, case-insensitive `"stop" in type_str` fallback. Robust against Python 3.11+ Enum stringification (`str(OrderType.STOP)` → `"OrderType.STOP"`).
- Used in: `place_bracket_order` (naked-order guard), `submit_entry`, `check_fills`, `attempt_day1_reentry`, `_process_entry_fill`. Never re-implement the loop.
- `_process_entry_fill` checks 3 sources before remediation: WS event legs, DB `stop_order_id`, REST refetch.

## Bracket-leg stop semantics (#508, 2026-08-04 — empirically established)

- A stop that is an OTO/bracket LEG (every MAGNA53 entry's stop) **cannot have its qty changed** — Alpaca rejects with `42210000 "qty cannot be changed for advanced orders"`, and the original leg stays LIVE after the rejection (atomic). Price-only replace works, but the replacement **remains a leg** (`order_class=oto`) — replacing never detaches it. A second stop, or any sell, is rejected `40310000` while the leg holds the shares. Probe + raw responses: `scripts/probes/_508_oto_leg_probe.py` / `_508_oto_leg_probe_output.json`.
- Consequence: a partial exit on a bracket-protected position MUST cancel the leg first. `order_manager._reduce_stop_via_cancel_new` is the only sanctioned way to do that: verified cancel → **gate on `qty_available` release** (the share reservation clears ~60ms AFTER the cancel confirms — the IBM 2026-05-27 race, measured) → new reduced stop (retry on reservation lag) → verify live → sell. Toggle `partial_exit_leg_safe` (default OFF). Simple stops keep the atomic qty-replace.
- After the first leg-safe partial, the position's stop is a SIMPLE stop — subsequent qty/price replaces work normally.
- `_order_to_dict` carries `order_class` (`'oto'/'oco'/'otoco'/'bracket'/'simple'`) — the leg-detection signal. Do not drop it.
- **#523 (2026-08-18, same bug class, second site) — `order_manager._ensure_stop_coverage`'s under-covered-repair branch hit the identical 42210000 rejection whenever the surviving stop was a leg** (a full-size bracket leg is never under-covered by itself; reaching this branch needs the position to grow past the leg or the leg to partly die). `stop_coverage_repair_failed` audit rows were checked and are ZERO in prod to date — no measured live cost. Fixed by extracting the shared mechanism out of `_reduce_stop_via_cancel_new` into `_replace_stop_leg_via_cancel_new` (cancel → release-gate → new-stop, direction-agnostic); `_reduce_stop_via_cancel_new` is now a pure thin wrapper (unchanged signature/behavior) and `_widen_stop_via_cancel_new` is the new sibling used by `_ensure_stop_coverage`, gated by the SAME `partial_exit_leg_safe` toggle. **Widening is not symmetric with reducing**: a reduce's new qty is always `<=` what the cancel itself frees, so the release gate can only ever find enough; a widen's new qty is by construction LARGER than the leg's own qty, so `_ensure_stop_coverage` runs a pre-flight `get_position` read BEFORE ever cancelling the leg — if broker truth shows insufficient headroom, the leg is never cancelled and the repair fails exactly as it always has (old leg stays live, `stop_coverage_repair_failed` audit, operator told). If the leg IS cancelled and the new stop then can't be placed (`naked`/`stop_filled` outcomes — e.g. a fill raced in, or a transient broker error after cancel), `_ensure_stop_coverage` does NOT place a stop off the (possibly now-stale) `target` qty; it alerts plainly that coverage may be zero and defers to the next reconciler pass, which re-reads broker truth from scratch. Not yet broker-confirmed live (no paper-broker probe run) or deployed — see `PLAN.md` #523.
- **#596 (2026-08-26) — the widen pre-flight sized headroom on the leg's ORDER quantity, and a partly-filled leg no longer holds that many shares.** `partially_filled` is a live-stop status (`_STOP_CONFIRMED_LIVE_STATUSES`), so a leg that has already sold part of itself reaches the widen branch carrying its full order qty. Cancelling it releases only its UNFILLED remainder, so the check over-stated headroom by exactly `filled_qty`. A partial fill alone does not trip it — the position shrinks by the same amount — but a partial fill PLUS any share reservation the target does not account for does, which is the exact situation the pre-flight exists for: the check passed, the leg was cancelled irreversibly, the release gate then timed out short and the replacement was rejected, leaving the position genuinely naked. Fixed: the pre-flight now sizes on `_leg_unfilled_qty(live_stop, live_qty)` — order qty MINUS filled qty — and an unreadable `filled_qty` REFUSES the widen rather than defaulting to zero (same idiom as a missing `stop_price`; a real broker dict always carries the field). Quantity only; no stop price, target or size changed. Evidence: `tests/test_523_eton_leg_widen_replay.py`.
- **#596 part 2 — a failed coverage repair now has a scheduled retry.** Previously a failure produced ONE 🚨 Telegram and nothing else: `check_position_coverage` (every 15 min) only DETECTS by design, and the next scheduled REPAIR is `sync_positions` inside `eod_cleanup` at 16:05 ET — so a 09:31 failure could sit unprotected for the whole session (~6h34m worst case; the 30-second `stop_ack_timeout_watchdog` closes it only when the cancelled leg is the one `stop_order_id` points at AND its once-per-trade-per-day remediation is still unspent). `order_manager.retry_failed_coverage_repairs` re-drives `_ensure_stop_coverage` off FRESH broker truth for any trade whose `stop_coverage_repair_failed` today is not followed by a `stop_coverage_repaired`, bounded to `_COVERAGE_RETRY_MAX_ATTEMPTS` **verified** attempts per trade per ET day (#599 — see the next bullet), driven by the `stop_coverage_repair_retry` scheduler job (every 5 min, 09:31-15:55 ET, both account modes — same scope as `sync_positions`, its other driver). **`stop_coverage_breach` never starts a retry, and a breach recorded after a failure ENDS one** — a stop above market is structurally un-retryable, the invariant converges on it by design, and the breach-exit decision is the operator's. Not a new mechanism: the same signed repair, driven again; every order decision stays inside `_ensure_stop_coverage`. **Worst case before:** 30-60s in the common case (the WS cancel nulls `stop_order_id` and the 30-second `stop_ack_timeout_watchdog` re-places at `orb_low`), but up to 09:31->16:05 (~6h34m) when that watchdog's once-per-(ticker,trade)-per-day remediation is already spent or the cancelled leg is not the one `stop_order_id` points at. **After:** ~5 minutes inside 09:31-15:55; a failure in the last minutes before the close still waits for the 16:05 sync (<=~9 min). ⚠ With the leg gone the retry lands in the PLACE branch. Until #600 (2026-09-03) that placed at `mi_live_trades.stop_price`, which can sit BELOW the lost leg's own price (breakeven withheld / never written — `docs/setups/exit_discipline.md` 2026-09-03); the retry only made that reachable every 5 minutes instead of at 16:05. See the #600 bullet below.
- **#599 (2026-08-26) — the retry counted a check it never performed as a success.** `_ensure_stop_coverage` returned `str | None` and `None` meant THREE things: coverage was CHECKED and meets target, a partial held the per-trade advisory lock (nothing checked), or the broker open-orders read failed (nothing checked). `retry_failed_coverage_repairs` collapsed all three with `healed = msg is None or msg.startswith("🛡")` — parsing the operator-facing Telegram emoji as a control signal — so a non-check was audited `healed=true` ("coverage now meets target") AND spent one of the six attempts. On recurring lock contention or broker flakiness a trade could burn the whole budget on passes that verified nothing, drop out of the retry set, and **the exhaustion 🚨 would never fire** because every attempt looked healthy. **Fix, at the source:** `_ensure_stop_coverage_outcome` returns a `CoverageOutcome(status, message, reason)` with `status ∈ {covered, unverified, repaired, flagged}`; `_ensure_stop_coverage` is now a thin wrapper returning `.message`, so `_sync_positions_for_mode`, `execute_partial_exit`'s abort + breakeven re-protect paths and `trade_stream`'s OCO-cancel re-protect are **unchanged** (they batch the string into a Telegram and correctly treat both no-op kinds as "nothing to say"). Only the retry reads `status`. **An `unverified` pass writes `stop_coverage_retry_deferred`, does NOT count as an attempt and does NOT report healed** — the trade stays in the retry set for the next 5-minute cycle, which is the point of having a retry; the returned dict gains `"deferred"`. An exception out of the invariant stays `flagged` (it already counts and already reaches the exhaustion alert — relabelling it would create a new silent path), and a breach is a verified check with a bad outcome, not a non-check. **No new alert was added:** a `get_open_orders` failure already fires the deduped alpaca API alert (#370) before re-raising, and the lock-held case is seconds-long by construction. The emoji prefix is untouched — it was always fine as display. No stop placement, threshold, exit rule or cadence changed.
- **#600 (2026-09-03) — a re-protect could re-arm the stop BELOW the last level the broker held.** `_ensure_stop_coverage`'s place branch (and its siblings: sync orphan remediation, both `trade_stream` cancel-restore paths, `update_stop`'s terminal-old-stop carve-out) placed at `mi_live_trades.stop_price`, which is deliberately allowed to understate the broker (the #548 breakeven-withheld branches; the market-mode fold-in never writes it). Fixed with ONE shared floor, `order_manager._apply_reprotect_floor`: the placed price is the DB price RAISED to the DB stop pointer's broker `stop_price` (terminal orders still carry it; `rejected` ignored) — and it **never refuses**: no pointer / unreadable / no price → the DB price is placed exactly as before, because an unprotected position is worse than a stop ~1R low. NOT routed through `update_stop`'s 08-10 floor: that one refuses against a LIVE stop (none exists on a re-protect), sizes from DB qty (the invariant sizes from broker qty), and cancels the pointer first. Coverage place branch reads the pointer fresh from the row, so every caller (`retry_failed_coverage_repairs`, `_sync_positions_for_mode`, `execute_partial_exit`'s re-protects, `_handle_oco_parent_cancel`) inherits it. One consequence surfaced as an operator fork, not decided: if the market already traded through the last broker level, the floored placement now breaches → converge + 🚨 (identical to an accurate-DB breach today) instead of accidentally re-arming lower. **Reach:** the floor needs the pointer to still name the dead stop; `_handle_cancel_or_reject` section 2 NULLs it on the WS cancel/expiry (`cancel_or_reject_null`, signed T1.5a) before the retry can read it, so in the common intraday path the retry still lands at the DB price — preserving the cancelled stop's level there is a second operator fork. Full record, sources and the tests: `docs/setups/exit_discipline.md` 2026-09-03. Deploy: `execution` + `market-agent`.
- **#545 (2026-09-06) — first PRODUCTION use of a price-only replace on a FULL-position leg, built DARK.** `order_manager.scan_breakeven_arms` (5-minute poll, after the profit trigger) moves the full-position OTO stop leg to entry with `alpaca.replace_order(stop_order_id, stop_price=entry)` — quantity untouched, so none of the 42210000 / reservation-race machinery above applies, and a rejected replace leaves the old leg live (the probe's T1b/P4 finding, now relied on in production for the first time; the #548 breakeven replace runs on the already-reduced simple stop). After the replace the stop **remains a leg** (`order_class=oto`), so a later partial still routes through the leg-safe path exactly as today. OFF until `mi_strategies.breakeven_arm_r` is set (NULL on every row → the scan returns before any read); the stop it targets, the raise-only guard and the failure outcomes are in `docs/setups/exit_discipline.md` 2026-09-06. Deploy when flipped: `execution` (broker code) + `market-agent` (scheduler wiring).
